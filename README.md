# 社团协同课表

> 别再对着一堆课表截图找时间了。

面向高校社团的课表收集与时间协调工具。成员维护自己的课表，负责人按日期和节次查看汇总，不再让所有人共同编辑一张容易误改的表格。

作品地址：<https://s0-capability-probe-uq2druqm8do.qoder.zone>

本项目是 **2026 Qoder 高校创造力大赛** 的参赛作品，这份仓库是参赛版本的源码。

## 一、介绍

这里是 wxy0641。社团成员的线上沟通大多发生在微信和 QQ，但熟人关系型即时通信并不适合社团的工作流：查一次活动时间，往往要翻聊天记录、逐张对照成员发来的课表截图。

“社团协同课表”先解决其中最具体的一环：**课程表收集**。成员按自己的课表填写并提交，负责人在一个页面里按日期和节次查看谁有课、谁没课、谁声明了忙碌，再决定活动时间。

目前它还是一个面向高校社团的小工具，不是钉钉、飞书那样的完整协同平台；但课表收集、日历共享和事件确认这条主链路已经可以实际使用。

## 二、这玩意能干啥

给高校社团成员填课、给负责人按日期和节次查课的协作网页工具。目前实现的功能包括：

- 注册、登录、登出
- 创建空间，用邀请码邀请成员加入
- 成员填写、保存草稿、整表提交课表
- 负责人查看课表收集、按日期和节次统计
- 按周导出 7 个工作表的 XLSX 文件
- 个人日历、日期例外（停课、忙碌、有空）
- 日期共享与告知同意，未共享的例外不会泄露
- 创建空间事件，向成员发出时间安排请求
- 成员接受后才占用对应节次，也可以拒绝
- 登录前集中告知、隐私设置和基础合规页面

一些边界：

- 一个账号不能代替另一个成员接受发给自己的安排；完整体验需要两个独立浏览器会话。
- 空白课表提交是合法的，表示“没课”，不等于没有提交。
- 只改草稿不会改变负责人看到的已发布版本。
- 演示时请不要上传真实成员资料。

## 三、制作动机

社团工作流有点“神秘”：消息散在微信和 QQ，课表是截图，活动时间靠人工对照。以个人能力做一个完整的协同办公平台不现实，所以先解决最影响效率的那一步——课程表收集。

目标不是替代聊天软件，而是把“谁什么时候有空”从截图和聊天记录里拿出来，变成可提交、可查看、可确认的数据。

## 四、怎么用

1. 打开作品地址，注册并登录；完成登录前的集中告知，日期共享按需选择（默认关闭）。
2. 创建一个空间，设置空间名称、收集模式、周次规则、教学周和时区；把邀请码发给成员。
3. 成员用邀请码加入，点节次填写课程；可以保存草稿，确认后整表提交。
4. 成员在“我的日历”处理具体日期；负责人在“课表收集”查看汇总，需要时点“导出课表”。
5. 负责人“新建事件”或“安排成员时间”并发送请求；成员在“待我确认与已接受”里自行接受，接受后才占用对应节次。

体验提示：完整体验建议用两个浏览器（例如普通窗口 + 无痕窗口）分别注册负责人和成员。项目当前没有密码找回，也没有邮箱绑定或验证码。

## 五、怎么做出来的

项目按阶段推进，每一阶段都先跑契约测试和浏览器测试，再做人工验收：

| 阶段 | 内容 |
| --- | --- |
| S0 | 验证 Qoder 的登录、数据库、权限和部署能力，跑通最小原型 |
| S1 | 注册登录、昵称、创建空间、邀请码加入、负责人与成员权限 |
| S2a | 课表填写、草稿与提交、版本条件写入 |
| S2b | 教学周、个人日历、日期例外与共享告知 |
| S3 | 课表收集、统计与 XLSX 导出 |
| S4 | 空间事件、安排请求与接受状态机 |
| S5 | UI 与交互优化、移动端适配、回归测试 |

开发过程中使用 Qoder 与模型辅助生成代码和测试，作者负责人工验收、交互取舍和发布判断。界面和文案经过多轮删改，不是一次生成后直接上线。

### 技术结构

- 前端：原生 HTML/CSS/JavaScript，无框架；`web/`
- 服务端：Deno Edge Function 模块；`functions/`
- 数据库：PostgreSQL `app` schema；`schema.sql`
- 密码：PBKDF2-SHA256，600000 次迭代，只保存盐和哈希
- 会话：HttpOnly、SameSite=Lax Cookie，服务端只保存令牌摘要
- 并发：课表、日期例外与事件更新使用版本条件；写请求带请求号，支持幂等重试
- 导出：服务端生成 XLSX，按所选日期所在周输出 7 个工作表
- 字体：Noto Sans SC 子集本地自托管，按 SIL Open Font License 1.1 分发

### 目录

```
functions/     路由、校验、会话、日历投影、收集、事件与导出
web/           静态前端与字体
dev/           契约测试、浏览器测试、内存假数据库与本地预览
schema.sql     PostgreSQL 表结构（app schema）
```

## 六、本地运行与测试

需要 Node.js 22 或更高版本。


本地预览只用于前端状态回归，账号与数据都在内存中，重启即清空。

这些测试直接调用真实服务端模块，只把数据层替换为内存假数据库；它们不能替代真实数据库、网关准入或托管环境的全链路验收。

## 七、部署说明

本项目按 Qoder Sites 的 Edge Function 形态编写，`functions/index.ts` 依赖部署时注入的 `./_qoder/backend.mjs`（平台适配层）。该文件不在仓库中，因此克隆后不能直接作为独立服务启动；本地可用 `dev/preview-server.mjs` 运行前端与路由逻辑。

部署到兼容环境时需要：

1. 配置 PostgreSQL，并执行 `schema.sql` 创建 `app` schema 与表。
2. 设置环境变量 `APP_PUBLIC_ORIGIN`，值为站点完整来源（例如 `https://example.com`），用于写请求的来源校验；未配置时相关请求返回 `application_auth_not_configured`。
3. 让静态文件（`web/`）与函数路由同源；前端固定请求 `/functions/v1/app`。
4. 由平台提供 `createSiteContext`、`createDatabaseClient` 与 `errorResponse` 适配，或自行实现等价适配层。
